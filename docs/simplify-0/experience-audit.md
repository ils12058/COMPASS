# Experience audit

Evidence is anchored to `0101a5d03c69c6f46fdf6b961a0a2de0ea73a122`. **A** = essential protection; **B** = legitimate complexity unnecessarily exposed; **C** = unjustified interaction friction; **D** = institutional decision required. A finding may contain more than one category. **High** means repeated workflow cost or a major dependency for simplification; **Medium** means a meaningful readability/interaction improvement. These are UX priorities, not security vulnerability ratings.

## Organization Catalog: ten workflow traces

Common protections: eligible active staff plus explicit `organization.catalog.manage`, independent relationship authority, cookie session/CSRF, current actor/session checks, recent server-verified MFA on mutations, input validation and transactional Audit. Existing records additionally use expected versions. Code/UUID/parent stay fixed after creation. See [service authorization and mutation boundary](../../be/compass/organization/catalog_services.py#L107), [API request schemas](../../be/compass/organization/api.py#L576) and [frontend authority/review](../../fe/src/features/organization/structure/catalog/catalog-editor.tsx#L70).

| Workflow | Current user-visible path and inputs | Checks, recovery and genuine consequence |
| --- | --- | --- |
| Create Campus | Add campus → code, official name, explicit initial status, required basis → Review change → Add campus → saved state/Done. | Global code uniqueness; normalized reserved identity, including inactive entries. Required name/basis ≤160 characters, code ≤32. Creation warrants review because stable code cannot be corrected through ordinary editing. |
| Create College | Campus Actions → Add college → same fields → review → Add college. Chosen Campus is fixed context, not a repeated selector. | Parent re-read; active ancestry required for active use; College code uniqueness within Campus. Do not infer Registrar/SIS code authority from the UI's “official identifier” wording. |
| Create Program | College Actions → Add program → code/name/status/basis, classification and Year Level policy; configured policy adds explicit level choices → review → Add program. | Fixed College, coherent policy, no inferred defaults. Incomplete Program may be created inactive; active creation requires known classification/configured levels. Noncontiguous levels stay exact. |
| Rename any entry | Actions → Rename → new name and required basis → Review change → Rename → saved state/Done. Current code, ancestry, policy and version also appear. | No-op rejected; stable identity preserved. Current linked labels may change; finalized saved facts/documents are not regenerated. Two actions after entry today: Review change, then Rename. |
| Update Program settings | Actions → Edit academic policy → prefilled classification/status/levels plus basis → current/proposed review → Save Program policy. | Complete policy tuple, expected version; requested/prepared current-student F4 requests block changed policy; unchanged policy remains a no-op. Submitted Inventory facts and issued certificates are not recalculated. |
| Activate | Actions → Activate → required basis → review → Activate. | Active ancestry and complete Program policy; no descendant activation or restoration of historical assignments. Meaningful status change merits explicit consequences. |
| Deactivate | Actions → Deactivate → basis and automatically loaded impact → Review change refreshes impact → Deactivate. | Blockers disable review; server recounts under lock at save. Campus/College blockers include active child Colleges/Programs, active Student-role affiliations across CURRENT/GRADUATED/FORMER lifecycle values, any Counselor responsibility, open Office threads and pending OPERATIONAL Follow-Ups through current affiliation. Program deactivation has warnings rather than invented affiliation/Responsibility blockers. Warnings/history are not blanket blockers. No cascade or reassignment. |
| View history | Actions → Change history → record-specific dialog → Previous/Next as available → Close. | Action label, time, versions, actor UUID, basis and before/after values. No global Audit or Accounts lookup; initialization history is not reconstructed. |
| Expired recent MFA / missing setup | Confirmed mutation is refused → Verify authenticator or open setup in a new tab → return, refresh → Review change → confirm again. | Inputs retained; completed verification performs reads only. Ownership/authority, latest target and relevant impact are rechecked. No automatic replay. MFA remains a supported control. |
| Stale/conflicting/uncertain save | Conflict closes review, retains draft and reloads current values; person reviews again. Interrupted/5xx result blocks further mutation and checks detail/history. | Duplicate code, inactive ancestry, pending F4, missing target and lost authority get distinct safe recovery. Matching actor/action/basis/version/values can confirm a committed write; otherwise Check saved state repeats reads only. Confirmed save with failed refresh offers read-only Retry refresh. |

### Change-note options: a separate decision

[API schemas](../../be/compass/organization/api.py#L580) and [service boundary](../../be/compass/organization/catalog_services.py#L155) require bounded nonblank basis; [Audit](../../be/compass/organization/catalog_services.py#L233) records actor, time, target, changed fields, before/after and basis automatically. [ORG-0 D4](../org-0/open-decisions.md) proposes bounded evidence “where appropriate”; [ORG-4 D4](../org-4/institutional-decision-register.md) remains OPEN / NOT APPROVED. Neither proves a universal institutional mandate.

| Future option | Assessment |
| --- | --- |
| No manual note for routine changes; automatic Audit only | Least input; plausible for spelling fixes, but removes optional useful context. Requires coordinated contract/reconciliation handling. |
| Optional Change note for routine changes | **Preferred candidate**: automatic Audit supplies factual accountability, person adds useful context when needed. Not approved or implemented. |
| Required Change note for selected consequential actions | Pair with the candidate above only after owners identify actual actions needing reasons, such as deactivation or eligibility changes. Do not invent a mandatory memo, approver or evidence upload. |
| Required Change note for all changes | Retain if an actual approved requirement is established. Current backend enforcement alone is insufficient evidence. |

The safe immediate SIMPLIFY-1 boundary keeps requiredness. A later contract change must account for old clients, optional/null/blank representation, historical basis values, Audit validation and frontend reconciliation equality; it must not insert fabricated notes such as “routine change.”

### Program and Organization responsibility boundaries

[Persisted policy validation](../../be/compass/organization/program_policy.py#L9) supports Bachelor's/Master's/Doctoral classifications and configured unique sorted integer levels 1–10, including gaps. Pending levels are null; no universal four-year assumption is valid. [Inventory](../../be/compass/inventory/services.py#L564) consumes configured membership; pending/unknown policy retains recorded Years 1–10 compatibility, not an academic-policy approval. [Good Moral eligibility](../../be/compass/good_moral/services.py#L458) preserves Bachelor/F4 template limits; Program Year 5 does not extend F4 Years 1–4. F6 degree suggestions are advisory, not verification of historical qualifications.

[Responsibilities](../../fe/src/features/organization/responsibilities/responsibilities-page.tsx) and [Student affiliations](../../fe/src/features/organization/student-affiliations/student-affiliations-page.tsx#L475) remain relationship work with separate `organization.manage` authority and routing/scope consequences. Catalog edit permission must not gain those rights. Simplify presentation around these boundaries; do not add automated reassignment, transfers, code reuse, effective-dated Registrar rules or academic approval workflows.
