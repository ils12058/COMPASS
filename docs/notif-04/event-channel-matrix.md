email resolvers, `push_policy.py`, API views/services and frontend routing on the
NOTIF-04 baseline. **30 events; 29 email-enabled; 15 rich candidates; 24 Push-eligible.**
This updates the NOTIF-01 identity inventory with NOTIF-02/03 delivery semantics.

M = mandatory operational; S = mandatory security; O = optional informational.
Optional preference affects Feedback email only. All events persist in-app intent;
Follow-Up/reminder self-list filters remain independently authoritative. Push also
requires enabled deployment, opt-in subscription, current owning session/account,
source policy and active recipient. It always opens Notifications Center, not a
resource-specific record; the service worker may replace unrecognized fixed copy
with a more generic message. No rich fields are copied to Push.

External tiers: **A** explicit candidate operational fields, **B** fixed minimal
operational copy, **C** specialized security copy. `minimal` never admits A. Rich
fields require exact `operational_v1`, source/recipient proof and a trusted action.

## Identity and destination qualifications

The Scheduled producer includes Fixed-Date Slot `book_fixed_slot`, targeting the
canonical Appointment rather than a booking duplicate. Group registration source
UUID differs from parent target; change/reminder source UUIDs likewise differ from
Appointment targets. E-Counseling target is the Appointment UUID, never room/consent
credentials. Exit/Inventory reopen source IDs identify events, not target records.
Feedback uses `?opportunity={UUID}` (missing ID goes to self list); Group missing ID
falls back to `/portal/group-sessions/my`; Inventory goes to `/portal/inventory/current`.
Account Security uses the signed-in User identity and `/portal/account/security`;
operational email links exclude it. Shared summaries require their normal published
owner access. The shared 22-case fixture is checked from both Python and TypeScript;
Security ownership is tested separately. The full source/target text above retains
source-specific identities rather than assuming a universal UUID resource route.

F/T abbreviations in historical inventory mean Follow-Up/reminder currentness.
General generic families check active recipients rather than adding new source-wide
suppression. Existing historical in-app records remain useful without asserting
current authorization or source availability. Source APIs remain the authority.
