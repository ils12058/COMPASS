# Additive migration and release boundary

Migration: `be/compass/good_moral/migrations/0003_receipt_verification.py`, after verified GM-OR-1 `0002_receipt_identity_and_history`. Registered in `canonical_migrations.json`; baseline hashes and both historical Good Moral migration files stay unchanged.

Adds the verification table/constraints, protected nullable request references for preparation/final issuance and narrowly scoped PostgreSQL guards. No data import, policy grant, fee schedule, fictional inspection, writer-mode change or historical source rewrite runs during migration. Old issued null provenance is accepted. Existing source constraints and GM-OR-1 ownership/projection/history guards remain installed.

Guards reject original inspection rewrites/deletion/reassignment/reactivation; invalid metadata/method/fee snapshot; noncurrent/unbound/wrong-owner/terminal inspection insertion; new readiness/issue without exact evidence; wrong-request preparation/issue references and terminal provenance changes. Deferred guards require declared correction/cancellation/policy-replacement invalidations and preserve inspection history. SQL fee fields prove snapshot shape and revision consistency, not institutional approval or actor authorization; services supply those decisions. Database date guard uses UCN Asia/Manila; runtime date validation uses the canonical institutional helpers. A future timezone change requires coordinated review of frozen database semantics.

Fresh install, populated upgrade and empty-verification reverse/reapply are exercised on disposable PostgreSQL. Fixtures include duplicate legacy claims, blank/non-80 issued receipts and cancelled rows; source/claim values and null inspection provenance survive. Verification evidence makes reversal fail atomically. GM-OR-1 history reversal restrictions still apply independently. Tests that traverse the canonical baseline restore the latest 0003 graph and compare only fields present in that historical schema.

After evidence exists, preserve tables/references and use a compatible build or controlled pause; never drop verification/identity history or return to an old writable binary. No live recovery/unfence command is added.

Before any real activation: approve complete identifier/normalization scope; authorize private count inventory; reconcile reservations/projections and quarantine; drain every writer/old binary/seed; approve pending READY review and queue impact; install an approved fee definition/applicability/evidence; approve named inspector grants; complete GM-OR-3 UX, GM-OR-4 integration/UAT and separate deployment/cutover authorization. The existing importer remains synthetic-only. No environment flag can bypass its database writer fence. Production performance, recovery and restored-backup gap reconciliation need separate evidence.
