# Verification domain

`GoodMoralReceiptVerification` in `be/compass/good_moral/models.py` holds UUID, protected exact assignment FK, protected verifier FK, server-controlled aware `verified_at`, sole method `PHYSICAL_OR_INSPECTION`, policy ID/version, Decimal expected amount, PHP currency, structured fee-decision snapshot, globally unique operation UUID, SHA-256 intent binding and one-way attributable invalidation. There is no request-level mutable verified flag.

Inspection means the named authorized GCO employee personally inspected the presented physical OR and matched its number, date and actual printed amount to this Good Moral request. Entry, import, preparation and issuance timestamps never fabricate this assertion. The inspector may also be the recorder/preparer; no unapproved two-person rule is introduced.

PostgreSQL enforces one active attestation per assignment; valid method/positive expected PHP fee; complete invalidation metadata; existing eligible current BOUND owner; complete matching fee/date evidence; immutable original attestation; protected deletion; monotonic invalidation; no revival or reassignment. Joined ownership and deferred eligibility checks prevent closing a verified claim or cancelling its request without invalidation. Role/capability and approved-policy resolution remain service decisions, not a database substitute for institutional authority.

Receipt number/date/amount or display spelling changes that append a revision invalidate its attestation in the same transaction with `RECEIPT_REVISED`. The old identity stays reserved. Cancellation uses `CANCELLED` and retains all evidence. Unrelated certificate corrections preserve unchanged receipt inspection but clear preparation evidence and return READY to REQUESTED under the existing rule. No-op entry creates no inspection or invalidation.

`prepared_receipt_verification` binds preparation to the exact approved inspection. New active issuance stores protected `issued_receipt_assignment` and `issued_receipt_verification`; its fee decision remains immutable on the referenced attestation. Database guards validate same-request/same-assignment pairing and protect terminal provenance. Historical issued records retain null references. No redundant fee ledger or issuance snapshot object is needed.

When a new approved fee decision changes, a new explicit physical inspection can invalidate the old pending attestation with `POLICY_CHANGED`, append a replacement under the unchanged assignment and return READY to REQUESTED. Existing issued attestation/provenance never changes because the current provider changes or becomes unavailable. Historical operational display uses recorded evidence; downloads do not consult new receipt gates.

An exact committed operation replay preserves original inspector/time and returns current request detail plus `receipt_verification_result` identifying the original attestation and its current invalidation time. Changed actor/request/reviewed version/revision/method under that UUID conflicts. Replay after correction/cancellation/issuance cannot revive the old record. A different operation against an unchanged already inspected revision returns a deliberate `already_verified` conflict rather than replacing the inspector or recording an unperformed second inspection.
