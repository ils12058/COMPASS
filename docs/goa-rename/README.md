# GCO-ALIGN-1 — Rename Guidance Services Staff to Guidance Office Assistant (GOA)

Date: 2026-11-08. Branch: `integration/ux15-modernization`.

This is a pure identity rename. The role that was `GUIDANCE_SERVICES_STAFF` is now
`GUIDANCE_OFFICE_ASSISTANT`, displayed as **Guidance Office Assistant** and abbreviated **GOA**.
No capability grant, designation, override, College scope, supervision scope, or business rule
changed. A GOA can do exactly what a GSS could.

## What changed

- **Identity policy** — `be/compass/accounts/policy.py` renames the role definition and its
  `ROLE_CAPABILITY_GRANTS` key, keeps the same capability set, updates
  `CATALOG_ELIGIBLE_ROLES`, and updates `GENERAL_GUIDANCE_INTAKE` compatibility.
- **Persisted role** — one additive data migration,
  `be/compass/accounts/migrations/0003_rename_guidance_services_staff_role.py`, renames the same
  `Role` row in place. It is registered under `additive_migrations` in
  `be/compass/common/canonical_migrations.json`.
- **Backend consumers** — role-code queries, scope filters, presentation labels, email copy, and
  handler-role enums across the backend now use the new code.
- **Staging seed** — the two synthetic assistant personas, emails, handles, scenario ids
  (`GOA-REF-01`, `GOA-REF-02`), report count, and verify output say `goa`. Seeded people remain
  synthetic.
- **Frontend** — role labels, access checks, Overview/help copy, the assistant Home
  (`goa-home.tsx`, `GoaHome`, `GOA_HOME_PREVIEW_SIZE`), and test fixtures use the new code and
  identifiers (`goa`, `head_goa`, `is_goa`, `world.goa`, `goaWorld`).
- **Contract and client** — `contracts/openapi.json` was regenerated by
  `export_openapi --settings=tests.settings`; exactly four enum values changed
  (`GuidanceHandlerRole`, `OrganizationRole` in two places, `RoleCode`). The orval client was
  regenerated with `pnpm api:generate`; neither file was hand-edited.
- **Docs and Help** — current READMEs, operational docs, the capability catalog audit, the staging
  dataset doc, the frontend copy guide, and in-app Responsibilities Help use the new name. Old
  slice docs, ADRs, archived frontends, and stored evidence keep the historical term.

## Migration behavior

The migration only renames a row; it never deletes or re-creates one.

- **Fresh install** — the canonical baseline has no role rows, so the migration is a no-op. The
  following `sync_identity_policy` creates `GUIDANCE_OFFICE_ASSISTANT` and its grants.
- **Upgrade from GSS** — the migration locks the matching `Role` rows, confirms that only the old
  identity exists, and updates `code` and `name` in place. The primary key survives, so every
  `User.role`, `RoleCapability`, `DesignationCapability`, `UserCapabilityOverride`, and legacy
  provider-role link stays attached. The following `sync_identity_policy` updates that same row
  and grants; it does not create a second role.
- **Both identities exist** — the migration stops with a clear `RuntimeError` naming both codes and
  changes nothing. Resolve the duplicate identity manually, then retry. The reverse step performs
  the same check in the opposite direction.
- **Rollback** — `migrate accounts 0002_student_session_summary_capabilities` renames the row back
  to `GUIDANCE_SERVICES_STAFF` with its original display name, again keeping the primary key. It is
  a no-op when the GOA row is absent and stops if both codes exist.
- **Deploy order** — deploy backend and frontend together, because the role code appears in the
  session payload and in generated enums; there is no compatibility alias. Run `migrate` before
  `sync_identity_policy`. If sync runs first it creates a fresh GOA role, and the later migration
  stops on the collision instead of guessing. The deployment entrypoint already applies migrations
  before policy sync.

## History is not rewritten

Existing audit events, notification rows, activity metadata, and append-only evidence may still
contain the old code or display name. They were not edited. No current screen renders a stored
historical role code or name directly: role labels and eligible-people role options come from live
`Role` rows and the current API enum, and audit/notification views render curated text rather than
raw role codes. No old-code display alias was therefore needed.

The provisional Faculty Referral activation policy signs its fixed role constraints in a digest.
Its append-only v1 evidence rows are left untouched; the policy is now
`code_owned_provisional_v2` with new fixed event ids (`f3b00001`–`f3b00005`) so old v1 rows remain
valid history and current validation matches the current role code.
