# Read Audit and disclosure privacy

The new bounded action is `counseling.continuity.source_read`, registered in the existing Audit action module. Every successful selected Encounter/Evaluation preparation appends one synchronous `record_event` in the same durable transaction. Target is the Grant; actor must match the authenticated receiving Counselor. No automatic retry or notification event is added.

Allowed metadata is explicitly constructed: Grant/receiver/Student/source UUIDs, source kind, fixed projection, Grant version, operational policy version/reference, disclosure policy version/reference/digest. `occurred_at` remains the existing Audit event timestamp. The digest identifies the approved field/evidence manifest; it is not a hash of decrypted clinical content.

No rating, special concern, recommendation, Intake concern, raw request/response, clinical reason, ciphertext, credential or key enters Audit. Denials do not append guessed source identities to an unauthorized activity feed. Existing append-only application Audit behavior and curated activity allowlists remain unchanged; this creates no blanket Head/DPO/IT inspection UI. Actual monitoring/retention authority still needs institutional approval.

Required Audit persistence failure prevents return of the prepared projection and rolls back any attempted event. The final post-insert recheck also rolls back an event when authority/time expires during Audit persistence. Concurrent failed/successful reads leave only the successful event. HTTP crypto/Audit failures are tested for safe errors, no professional sentinel in responses/logs and no body release. An authorized read event attests server-side authorized preparation/commit, not guaranteed network delivery or human comprehension.

The existing `ContinuityNoStoreMiddleware` already covers both child routes. Success, authentication, authorization, policy, stale-version, validation, source-conflict, unavailable-content and internal Audit failure responses use `Cache-Control: private, no-store`; no second middleware is introduced. No encrypted/protected body, presigned URL, streaming response or export leaves this mechanism.

Routine content uses its existing authenticated record/section binding and dedicated keyring. The authorized adapter decrypts only Counselor Evaluation and explicitly selects policy-approved fields. Malformed Intake ciphertext does not trigger Intake decryption or become a reason to disclose it. Existing Summary, Referral, Assessment, Inventory and E-Counseling content functions are not traversed; tests spy on those boundaries. Publication, email, Push, realtime and Student notice behavior are unchanged.

CONT-3 must treat protected query data as transient account/Grant/source/version-owned memory. Clear it on authorization loss, exact expiry, revocation and account change; reject late in-flight responses after an authority generation change. Never persist it in localStorage, sessionStorage, service-worker/HTTP API caches, URLs or telemetry. Realtime is an invalidation hint, never authority; every read reauthorizes. No frontend viewer is added in CONT-2B, and no browser/cache UX claim is made here. Already viewed information remains subject to institutional confidentiality and accountability; server denial cannot recall it.
